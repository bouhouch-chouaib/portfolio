## The problem

A significant share of city-centre congestion is generated by vehicles looking for a parking space. The Eurométropole de Metz publishes data from connected car parks, but the information stays fragmented and unusable for a driver behind the wheel.

The goal: aggregate heterogeneous feeds from several cities and turn them into immediate decision support — which space, where, and how to get there.

The application covers eight cities: Metz, Lille, Lyon, Paris, La Rochelle, Toulouse, Marseille and London. It offers map browsing, pricing, favourites, booking with capacity checks, and accessibility filters (reduced-mobility spaces, electric charging points).

## My role

Front-end and algorithms: the map interface, geolocation, and route computation with recalculation mid-journey.

## The constraints

- **A different data format for every city**, to be unified into a single internal model.
- **A map has to stay smooth.** Every unnecessary render shows on screen, especially with many dynamic markers.
- **CORS restrictions** on public feeds consumed directly from the browser.
- Five people, two-week sprints, with a firm delivery date.

## What I measured

- **Eight cities integrated**, one of them outside France, which served as a real test of the adapter layer.
- **288 estimated effort points** for the complete project, 144 of them for the minimum viable product. US03, real-time guidance, was estimated on its own at 89 points — a signal of major technical risk, and treated as a priority for that reason.

## What went wrong

The difficulty did not come from the features but from the tool. Mapbox GL JS exposes a large number of components — layers, sources, controls, the Directions API — and each of them works in a particular way that is not necessarily the way you need. Getting exactly the behaviour we wanted took far longer than expected: understanding which component did what, which to use for which effect, and how to make them coexist in a React application without breaking rendering.

The same problem came up with every feature we wanted to add beyond the specification. An idea that was simple to state almost always ran into the question of whether the library allowed it to be done cleanly, or only by working around it. **That trade-off — building with the tool or against it — took up a significant part of the project.**

## What I take away

Integrating a powerful library costs time before it saves any. The real work was not writing features, but learning what each building block of the tool was for and what it would accept being asked to do.

I also take away the value of a pivot decided on a measurement. Abandoning Leaflet mid-project was expensive, but the decision rested on load tests, not on a preference. That is what made it defensible to the rest of the team.
