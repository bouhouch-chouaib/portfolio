## Le problème

Le département informatique de l'IUT de Metz organisait le placement des étudiants en salle d'examen avec une application interne vieille de plus de quinze ans. Elle fonctionnait, mais accumulait une dette technique lourde : code mêlant PHP, SQL et HTML sans séparation, appels `mysql_*` obsolètes, mots de passe stockés en MD5 avec un mot de passe par défaut codé en dur, navigation par iframes imbriquées, base de données non normalisée.

Le point le plus révélateur : la disposition d'une salle était stockée dans un unique champ texte, sous forme de chaîne brute du type `31011111013…`. Aucune requête SQL ne pouvait porter sur un siège particulier ; toute la logique était déportée dans le code applicatif.

Après audit, l'équipe a choisi de reconstruire plutôt que de rafistoler.

## Mon rôle

Back-end et sécurité, au sein d'une équipe de quatre en méthode Scrum. Trois chantiers : la refonte et la normalisation de la base de données, le système d'authentification et de gestion des sessions, et l'export des données.

## Les contraintes

- **Une application réellement utilisée** par les enseignants et l'administration du département : reprise des données existantes et continuité fonctionnelle non négociables.
- **Des contraintes métier non triviales** : étudiants à mobilité réduite, tiers-temps, espacement anti-triche.
- **Un projet noté sur la rigueur**, avec un enseignant référent qui lit le code à partir de la modélisation.
- Quatre personnes, des sprints hebdomadaires.

## Ce que j'ai mesuré

- **Six tables de liaison supprimées** (`devoir_groupe`, `devoir_promo`, `enseigne`, `placement`, `surveille`, `matiere`), la logique d'affectation étant centralisée dans une seule table.
- **Élimination des champs calculés** : le décompte d'étudiants par groupe, auparavant stocké dans un champ dénormalisé sujet aux anomalies de mise à jour, est désormais obtenu dynamiquement.
- **Typage resserré** : attributs booléens stockés en `INT(11)` convertis en `TINYINT(1)`, clés étrangères optimisées.
- **Deux bibliothèques PDF concurrentes** (ezpdf et fpdf) remplacées par une seule.

## Ce qui a raté

L'export PDF a été de loin la partie la plus difficile, et j'ai passé plus de temps dessus que prévu. D'abord pour choisir la technologie : deux bibliothèques obsolètes coexistaient dans l'ancien code et faisaient doublon, et il fallait trancher entre les remplacer par un équivalent moderne côté serveur ou déporter la génération côté client. Ensuite pour obtenir un rendu visuellement acceptable — un plan de salle exporté doit rester lisible par un surveillant sur une feuille A4, ce qui est une contrainte plus dure qu'elle n'en a l'air. La solution retenue reconstruit dynamiquement un document HTML épuré, sans éléments d'interface, avant de le convertir en PDF paysage.

Mais la vraie difficulté du projet était ailleurs : **construire une version propre par-dessus un existant bancal.** Chaque décision devait tenir compte de ce que l'ancienne application faisait, de ce que ses utilisateurs attendaient, et de ce qu'il fallait absolument ne pas reproduire. C'était pénible, et c'est rétrospectivement le meilleur entraînement que j'aie eu au travail réel de refonte en entreprise — où l'on hérite presque toujours de quelque chose plutôt que de partir d'une page blanche.

## Ce que j'en retire

Une base de données mal conçue ne se corrige pas dans le code applicatif : elle contamine tout ce qui la touche. La chaîne `31011111013…` n'était pas un détail de stockage, c'était la raison pour laquelle aucune fonctionnalité intéressante n'avait pu être ajoutée à cette application en quinze ans.

J'en retiens aussi qu'un audit sérieux se fait sur le schéma avant de se faire sur le code. Les failles les plus graves que nous avons trouvées — la cascade destructrice, le MD5, le mot de passe en dur — étaient toutes visibles dans la structure, pas dans la logique.
